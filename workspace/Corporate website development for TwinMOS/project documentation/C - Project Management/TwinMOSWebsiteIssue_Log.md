## 1. Issue Log Overview

This document tracks all issues encountered during the TwinMOS corporate website redevelopment project. Issues differ from risks in that they are current problems requiring resolution, not potential future events.

**Issue Tracking:** GitHub Issues (primary) + this log (summary)  
**Escalation:** Per Communication Plan escalation path

## 2. Issue Log Template

| Field | Description |
|-------|-------------|
| **ID** | Unique issue identifier (ISS-YYYY-NNN) |
| **Date Raised** | When the issue was identified |
| **Raised By** | Person who identified the issue |
| **Category** | Technical / Resource / Schedule / Budget / External / Communication |
| **Priority** | P0 (Critical) / P1 (High) / P2 (Medium) / P3 (Low) |
| **Description** | Clear description of the issue |
| **Impact** | Effect on project scope, timeline, budget, or quality |
| **Owner** | Person responsible for resolution |
| **Target Resolution** | Target date for resolution |
| **Status** | Open / In Progress / Resolved / Closed / Escalated |
| **Resolution** | How the issue was resolved |
| **Date Resolved** | When resolution was achieved |

---

## 3. Priority Definitions

| Priority | Definition | Response Time | Escalation |
|----------|------------|---------------|------------|
| **P0 — Critical** | Blocks sprint goal or phase milestone; no workaround | 4 hours | Immediate to Team Lead + PM |
| **P1 — High** | Significant impact on deliverable; workaround exists but painful | 24 hours | To PM within 24 hours |
| **P2 — Medium** | Moderate impact; acceptable workaround | 3 days | To PM at next standup |
| **P3 — Low** | Minor impact; cosmetic or convenience | 1 week | Logged; no escalation |

## 6. Issue Resolution Workflow

### 6.1 Issue Identification

1. Any stakeholder can raise an issue
2. Log in GitHub Issues with label `issue-log`
3. Notify TwinMOS PM via Slack/email
4. PM assesses priority and assigns owner

### 6.2 Issue Triage

| Step | Action | Owner | Timeframe |
|------|--------|-------|-----------|
| 1 | Log issue with full details | Reporter | Immediate |
| 2 | Assess priority and category | TwinMOS PM | Within 4 hours |
| 3 | Assign owner and target date | TwinMOS PM | Within 4 hours |
| 4 | Acknowledge and begin investigation | Issue Owner | Within priority response time |
| 5 | Update status and progress | Issue Owner | Daily until resolved |

### 6.3 Issue Escalation

| Condition | Escalation Path | Decision Maker |
|-----------|-----------------|----------------|
| P0 issue unresolved > 4 hours | Team Lead → PM → Operational Sponsor | Operational Sponsor |
| P1 issue unresolved > 24 hours | Owner → PM → Team Lead | Team Lead + PM |
| Issue affects milestone | PM → Operational Sponsor | Operational Sponsor |
| Issue requires budget > $1K | PM → Operational Sponsor → Sponsor | Project Sponsor |
| Issue requires scope change | PM → Operational Sponsor | Operational Sponsor |

### 6.4 Issue Closure

1. Owner confirms resolution
2. Reporter validates fix
3. PM updates this log
4. Lessons learned captured (if significant)
5. Related risks updated if applicable
